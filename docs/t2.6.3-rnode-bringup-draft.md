# T2.6.3 draft — RNode / LoRa bring-up checklist (working notes)

**Status:** DRAFT / working notes, not the finished T2.6.3 ticket. This is the
hardware bring-up checklist and the Reticulum interface template you need to take
a real RNode-class radio (e.g. a **ThinkNode M1**) from "in a drawer" to "carrying
station traffic over LoRa." The transport itself is done and carrier-agnostic
(T2.6.2): moving from the TCP interface to a real radio is a **config + firmware**
change, not new transport code — the airtime budgeter and `DtnSyncer` do not
change at all.

The actual radio bring-up is **human-run** (flashing firmware, over-the-air
testing); this doc is what you drive by hand, and the config stanza is what
T2.6.3 will teach the sidecar's `render_reticulum_config` to generate (it
currently emits only the TCP interfaces — `crates/rrn-station/src/sidecar.rs`).

---

## 0. Will *this* board work? (the gating question)

Reticulum talks to LoRa through its **`RNodeInterface`**, which drives a board
running **RNode firmware** over USB serial. So the device must:

1. carry a **Semtech LoRa transceiver** — SX1276/78 (SX127x) or SX1262/68
   (SX126x); newer handhelds are usually SX1262;
2. be on the **RNode firmware supported-boards** list (`markqvist/RNode_Firmware`)
   — common supported MCUs are **ESP32** (LilyGO T-Beam/T3, Heltec LoRa32) and
   **nRF52840** (RAK4631-class);
3. match your **regional LoRa band** (868 MHz EU / 915 MHz US), agreed on both
   ends.

**Definitive check (5 minutes, no code):**

```sh
# with the pinned venv from T2.6.1:
/tmp/rns/bin/rnodeconf --autoinstall
```

`rnodeconf` detects the connected board and offers firmware **only if it is
supported** — that is the authoritative yes/no. A device currently running
**Meshtastic** is a good sign (it *is* a LoRa board); a supported one can be
**reflashed** to RNode firmware (the two firmwares are mutually exclusive — you're
converting it, not dual-booting).

> **ThinkNode M1 note:** confirm its LoRa chip + MCU from the spec sheet or from
> `rnodeconf`'s detection before ordering a second unit. If `--autoinstall` does
> not recognize it, it is not (yet) an RNode target, and the field test needs a
> known-good RNode instead (a LilyGO T-Beam or RAK4631 is the safe reference).

You need **two** radios to test an over-the-air hop: one on the station, one on a
peer. A single M1 only proves the station↔RNode USB path.

## 1. Flash + verify the RNode

```sh
# 1. Flash RNode firmware (interactive; pick your board when prompted).
/tmp/rns/bin/rnodeconf --autoinstall

# 2. Inspect the flashed device — confirms firmware, EEPROM, region.
/tmp/rns/bin/rnodeconf -i /dev/ttyACM0        # nRF52840 boards
#   (or /dev/ttyUSB0 for many ESP32 boards; `ls /dev/tty*` before/after plug-in)

# 3. One-time provision of frequency/bandwidth/SF via the config below, then:
/tmp/rns/bin/rnstatus                          # should list the RNode interface up
```

---

## 2. The Reticulum `RNodeInterface` stanza (the template T2.6.3 generates)

Add this to `<data_dir>/reticulum/config` under the existing `[interfaces]`
section (the sidecar generates the file on first run; it never overwrites your
edits). Values are **region- and link-specific** — the ones below are an EU-868,
conservative-range starting point.

```ini
  [[RNode LoRa Interface]]
    type = RNodeInterface
    interface_enabled = True
    # Serial port of the RNode (see `ls /dev/tty*`); nRF52 boards are usually ACM.
    port = /dev/ttyACM0
    # Radio parameters — MUST match on every node on this LoRa network.
    frequency = 867200000       # Hz  (EU 868 band; US 915: e.g. 915000000)
    bandwidth = 125000          # Hz  (125 kHz is the robust default)
    txpower = 7                 # dBm (start low; raise within legal limits)
    spreadingfactor = 8         # 7..12 — higher = more range, less throughput
    codingrate = 5              # 4/5
    # Optional identity beacon for a shared channel:
    # id_callsign = RRN-STATION-1
    # id_interval = 600
```

Throughput sanity: SF8 / 125 kHz ≈ ~2 kbit/s raw on air, and regional duty-cycle
rules cut *sustained* throughput to single-digit bytes/second — which is exactly
what the station's `[lora]` airtime budget already paces to
(`raw_bytes_per_sec × duty_cycle_percent`). Set `[lora] raw_bytes_per_sec` to the
measured on-air rate for your SF/BW once you have it (§4).

Then enable the transport in the station config (T2.6.2):

```toml
[sidecar]
enabled = true
# ... rnsd_path, config_dir ...

[lora]
adapter_script = "scripts/reticulum/lxmf_adapter.py"
# raw_bytes_per_sec / duty_cycle_percent tuned to your region + SF (see §4).
```

## 3. Two-node link test (over the air)

1. Flash **both** radios identically (same frequency/BW/SF).
2. Bring up `rnsd` + the station on each node (or one station + one bare
   `rnsd`/`rnx` peer).
3. On node A: `rnstatus` shows the RNode interface up; `rnpath` shows a path to B
   appearing after B announces.
4. Send a probe: `rnprobe lxmf.delivery <B-destination-hash>` — expect a reply
   with RSSI/SNR.
5. Then the real check: submit a small **DTN bundle** on A and confirm it is
   ingested on B and its **delivery receipt** returns to A — the same
   receive→ingest→receipt path the T2.6.2 harness proves over a mock, now over
   real air.

---

## 4. Field acceptance (what T2.6.3 signs off)

- [ ] `rnodeconf -i` confirms RNode firmware + correct region on both units.
- [ ] `rnstatus` shows the RNode interface up on both.
- [ ] `rnpath` resolves a path A↔B over LoRa (not TCP).
- [ ] `rnprobe` returns RSSI/SNR at the intended separation (bench, then field).
- [ ] A real signed `Bundle` crosses A→B over LoRa, byte-identical, and its
      receipt returns (mirror the T2.6.2 round-trip, now on air).
- [ ] Measure the **actual** sustained on-air bytes/second at your SF/BW/duty and
      set `[lora] raw_bytes_per_sec` / `duty_cycle_percent` to it; re-run and
      confirm economic traffic is paced ahead of bulk (the announce-budget number
      in the threat model becomes measured, not estimated — ADR-0013 /
      threat-model TODO).
- [ ] Range/So­ak: a multi-hour run at field distance with periodic bundles,
      asserting no lost economic records (couriers/paper remain the floor if the
      link drops).

---

## 5. What this does NOT cover

Real multi-hop mesh behavior at scale, antenna/RF tuning, regulatory compliance
sign-off, and the live community drill — those are field/operational work beyond
the code. If the ThinkNode M1 is not an RNode target, this checklist still applies
verbatim to a known-good RNode (LilyGO T-Beam, RAK4631); only the flashing step
differs.
