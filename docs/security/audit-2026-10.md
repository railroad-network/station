**Repository:** `station` (Railroad Network reference implementation)
**Commit audited:** `791db586e8d016a24d67edb76429344440495a2c` (2026-09-25)
**Performed by:** Claude (Anthropic AI model, Fable 5.1), operated by the project maintainer

## Disclosure and limitations

This audit was performed by an AI model, not by a professional security firm. It
is an internal review intended to raise the floor, not an attestation. Treat its
conclusions accordingly:

- It is a **code review with targeted reproduction**, not a penetration test.
  The workspace was split into ten review lanes, each read in full by a separate
  reviewer instance; every finding reported here was then re-checked against the
  code by the lead reviewer. Six findings were additionally **reproduced by
  running a test** against the audited commit; those are marked *Reproduced*.
  Everything else is marked *Traced* (confirmed by reading the full path) or
  *Plausible* (mechanism read, one step not confirmed).
- No fuzzing campaign, no side-channel measurement, no adversarial tooling
  against a live deployment, no real radios. The Linux-only encrypted-volume code
  (`storage/volume.rs`) was read, not run.
- **Absence of a finding is not evidence of absence.** An AI reviewer can miss
  bugs a human specialist would catch, and vice versa. The August review of the
  Phase 0–1 surface reported no High-severity findings; this one, over a much
  larger surface, reports five. That is a statement about how much was added and
  how much was looked at, and it should lower, not raise, anyone's confidence
  that a third pass would find nothing.
- A professional audit is still warranted before any deployment where real
  people depend on this software's guarantees.

Findings are described at the level needed to understand and fix them. Each
carries a concrete failure scenario rather than a hypothetical.

paired-device channel, DTN bundle, replica pull, paper ingest) held to the same

bytes; secrets' lifetime and file modes; subprocess construction; and each
security claim in the threat model, the red-team checklist and the runbook
checked against the code.

## Summary

Five High-severity findings, twenty Medium, fifteen Low, one Info. The
cryptographic core is still in good shape — the August assessment of the
primitives, canonical serialization, signature discipline and the Shamir
implementation holds, and the Phase 2 additions kept to it (every new signed
kind is domain-separated, every new decode boundary is depth-guarded, every
station-signed kind is signer-pinned on replay). What Phase 2 changed is the
*shape of the front door*. Three patterns account for most of what follows:

1. **The delay-tolerant door is permissionless, and the rules that assumed a
   paired member were not re-derived for it.** A key nobody has ever seen can be
   debited to the floor, earn standing, and write permanent records (RRN-A-016,
   017, 037).
2. **Party-asserted values still reach arithmetic.** ADR-0022 moved ledger,
   governance and dispute-pool windows onto the admission clock; contract
   schedules, jury verdict times, and prices' *signs* were left behind
   (RRN-A-014, 015, 021, 041).
3. **Short human-compared codes without a commitment.** The pairing code (32
   bits) and the recovery fingerprint (40 bits) authenticate the two ceremonies
   that guard keys, and both can be matched by an attacker who searches
   (RRN-A-023, 029, 030).

The single writer runs every request on one thread with no panic containment,
which turns any reachable panic or unbounded loop into a halt (RRN-A-013, 014,
035, 038).

## Findings

### RRN-A-013 · High — Malformed hex in an unauthenticated `/pair` request halts the writer

**Where:** `rrn-station/src/core.rs:7592` (`unhex`), `pairing.rs:156-186`,
`core.rs:5462`, `core.rs:762-768` (core thread spawn), `mobile_server.rs:92`.

`unhex` checks that a string's *byte* length is even and then slices it two
bytes at a time. A string containing a multi-byte character that straddles a
slice boundary makes the slice panic. `POST /pair` is the one request the mobile
listener serves before pairing (default bind `0.0.0.0:7500`, advertised over
mDNS), and its `token` and `signature` fields go straight through this decoder.

The panic happens on the single `rrn-core` thread. That thread is spawned
without panic containment and its handle is dropped, so the process stays up
(a supervisor sees nothing to restart) while every operator command, every
phone request, every sweep and every bundle ingest returns "core stopped" or
503. Nothing settles until someone restarts the daemon by hand, and the request
can simply be sent again.

**Reproduced.** Against a real station: one `/pair` request with a non-ASCII
`token` → `thread 'rrn-core' panicked … byte index 2 is not a char boundary`;
the next operator `whoami` returns `{"error":{"code":-32603,"message":"core
stopped"}}`.

The same decoder is reachable by a paired member through every `submit_*` hex
parameter and the id parsers, on a replica, and by a hostile station against the
CLI wallet (`channel_client.rs:182`).

**Recommendation.** A boundary-safe strict decoder (`s.get(i..i + 2)?`, or the
`hex` crate already in the tree; `from_str_radix` also accepts a leading `+`,
which a strict decoder fixes). Separately, make core death loud: contain a panic
per command and reply with an internal error, and exit the process if the core
thread ever ends, so a supervisor restarts it. The threat model's "one bad line
never takes down the daemon" should then be true of every field, not only of
JSON framing.

**Update (2026-10-09, PR #76) — fixed.** `unhex` now walks the string's
bytes in pairs and accepts only ASCII hex digits, so no input can panic it (it
also stops accepting a leading `+`/`-`); every caller — `/pair`, the paired
mobile's hex parameters and id parsers, the CLI wallet — shares the one
decoder. The core loop now catches a handler panic, answers the waiting caller
with an internal error, and exits the process (status 70) so a supervisor
restarts it from the log instead of leaving a live process with a dead core.
The reproduction above is a committed regression test
(`audit_regressions::unauthenticated_pair_request_with_multibyte_hex`): the
malformed `/pair` now gets a `400` and the core keeps answering.

### RRN-A-014 · High — One member's contract makes the charge sweep loop without bound

**Where:** `rrn-station/src/core.rs:2727-2815` (`do_charge_contracts`),
`rrn-marketplace/src/contract.rs:247-249`, `:302-315`, `:489-491`, `:517-532`,
`rrn-marketplace/src/listing.rs:721-740`, `rrn-marketplace/src/inquiry.rs:852-888`.

A recurring listing's terms are validated only for a non-zero duration, a
non-zero custom period and a non-negative penalty. A period of one second and a
duration of four billion periods are legal. A contract's `started_at` is "from
the buyer's own clock" and is compared to nothing. An inquiry may be opened by
the listing's own provider. The sweep then does, on the core thread:

```rust
while let Some(index) = records.next_due_charge(now, periods_charged) {
    … if !self.append_contract_charge(charge, &station, now) { break; }
    appended += 1; periods_charged += 1;
}
```

A single paired member publishes such a listing, inquires on it, agrees with
themselves, and signs a contract dated to the epoch. Every second since 1970 is
a due period: about 1.76 billion station signatures and log appends, during
which the writer serves nothing. Buyer and provider are the same address, so it
costs the member nothing. The contract is in the append-only log and the sweep
timer fires at startup, so a restart re-enters the loop; recovery needs a code
change or surgery on the database.

**Reproduced.** With the test clock at 1000 s: the listing validates, the
self-inquiry and the epoch-dated contract are admitted, and one sweep appends
1001 charges (one per elapsed second).

ADR-0018 accepts that contract charges are not floor-checked on the ground that
"contract terms are bounded and visible". Nothing bounds them. A comment at
`core.rs:7365` relies on "a handful of periods, never near `u32::MAX`".

**Recommendation.** A minimum period and a maximum duration in both validators;
schedule and notice anchored on the contract entry's *admission* time, as
settlement windows already are (ADR-0022); a cap on charges appended per
contract per sweep; refuse an inquiry whose buyer is the provider; and treat an
already-admitted contract that violates the bounds as inert on replay (skip,
never halt).

**Update (2026-10-09, PR #77) — fixed.** `Listing::validate` and
`ServiceContract::validate` now bound a recurring cadence: a custom period of at
least one hour, at most 366 periods (the lifetime bound on charges per
contract), at most 366 days' notice, and a penalty under the Tier-3 floor. The
sweep appends at most 24 period charges per contract per run, so a backlog
lands over successive sweeps and no contract holds the core thread; an
early-termination penalty waits until the backlog clears, so downtime cannot
change whether it is owed. The
schedule and the notice window run from the contract's and the termination's
admission (ADR-0022), with saturating arithmetic; `started_at` and
`requested_at` are testimony only. An inquiry whose buyer is the listing's
provider is refused (`BuyerIsProvider`) and skipped on replay. `contract::scan`
and `inquiry::scan` re-apply every new rule, so a hostile chain admitted before
this change is skipped, never halts replay, and is never charged. The
reproduction is a regression test in both forms: the hostile records are now
refused at the front door
(`contract_sweep_is_bounded_and_hostile_terms_are_refused`), and the same chain
appended raw makes the sweep append nothing
(`an_already_admitted_hostile_contract_is_skipped_on_replay`). Charges already
appended for a since-invalidated contract stay on the log as history.

### RRN-A-015 · High — Negative prices are accepted; the provider is debited

**Where:** `rrn-marketplace/src/inquiry.rs:216-224`, `:291-302`, `:643-648`,
`rrn-marketplace/src/contract.rs:162-168`, `:302-314`,
`rrn-station/src/core.rs:2763-2769`, `rrn-station/src/ledger_view.rs:79-90`.

An inquiry's opening offer and counter-offers are validated for length only. A
negotiable listing accepts *any* agreed price. A contract's per-period amount
must merely equal the agreed price. The balance fold subtracts a charge from the
buyer and adds it to the provider, with the comment "a contract only ever
charges in that direction" — so a negative per-period amount pays the buyer out
of the provider's balance, every period, for the provider's own stated duration.
The charge path has no debt-floor check and no tier check.

A buyer offers −20.00 on a negotiable recurring listing. The provider's phone
shows the action button as "Accept 20.00" (the companion mobile report,
RRN-M-011: the formatter takes the absolute value). One tap, and the station
does the rest.

**Reproduced.** Offer of −2000 centi admitted; `Agreed{-2000}` admitted;
contract at −2000 per period admitted; four sweeps later the buyer is at
+80.00 and the provider at −80.00 against a −20.00 debt floor.

ADR-0010 allows a negative *listing* price on the Commons surface (a subsidy the
provider chooses). Nothing covers a negative price chosen by the buyer.

**Recommendation.** A sign rule at the station, not only in the app: reject
negative offers, counter-offers and agreed prices unless the listing's surface
permits them, reject a non-positive per-period amount in
`ServiceContract::validate`, and hold a per-period amount to the Phase 1 tier
ceiling. Skip an already-admitted violating contract on replay.

**Update (2026-10-09, PR #77) — fixed.** A sign rule now holds at the
station, in all three inquiry append paths and again in `inquiry::scan`: on
Goods and Services an opening offer, counter-offer, and agreed price must be
`>= 0` (`NegativeAmountNotAllowed`); on Commons a negative amount is allowed
only when the provider's own listing is priced below zero (a published
subsidy), so a buyer can never flip who pays whom. `ServiceContract::validate`
refuses a per-period amount outside 1..=4,999 centicommons (positive, and under
the Tier-3 floor) and replay skips a contract that fails it. The reproduction is
a regression test (`negative_offers_and_agreed_prices_are_refused_on_goods_and_services`):
each negative step is refused, and the same chain appended raw is never charged —
the provider's balance stays at zero. The phone's sign display (RRN-M-011) is
the mobile report's.

**Update (2026-10-09, PR #78).** The one dead end the contract bound left —
a recurring listing that does not invite offers, priced where no contract can
charge — is closed by an ADR-0010 Clarification. `Listing::validate` now holds
such a listing's price to the same `1..=4,999` range at publish, at every
patch, and on replay of the creation record.

### RRN-A-016 · High — The delay-tolerant door admits debits from never-enrolled keys

**Where:** `rrn-station/src/core.rs:4599-4610` (DTN route) versus `:5776-5784`
(the channel binds the record's signer to the paired device),
`rrn-ledger/src/engine.rs:74-92`, `:171-254`,
`rrn-station/tests/it/outage_72h.rs:36-42`, `:172-202`.

On the live paths, a spending identity must be a device the operator paired
after an in-person code comparison. A bundle carries records from *any* key: the
entry must be signed by its author and the embedded record by its signer, and
that is all. The engine then applies the debt floor to that key — whose balance
is zero and whose floor is −20.00 Commons — and admits the debit. Nothing in
`rrn-ledger` asks whether the key belongs to anyone.

So the floor that ADR-0018 introduced to close the August finding RRN-A-007 is
per *key*, and keys are free. A paired member (as "courier", over their own
channel), anyone the operator ingests a sheet from, or anyone who can reach the
radio adapter generates a key, signs Tier-1 payments from it to an identity they
control, confirms them, and abandons the key at its floor. Repeat. The receiving
identity accumulates a positive balance that is spent with honest members; the
matching debt sits on keys that will never repay it.

**Reproduced.** Three never-seen keys each pay 4.99 to one receiver in a bundle:
every proposal and confirmation is `Admitted`; after the window the receiver
holds +14.97 and each throwaway key −4.99.

The outage harness asserts that an unknown key's proposal is admitted and calls
it harmless because "with no counterparty confirmation, [it] never settles"; a
colluding confirmer falsifies that. The red-team checklist's "Forge" row cites
that same harness leg for the opposite claim ("Refused `bad-signature`"), and
the threat model says "standing/membership is enforced … at ingest and in the
ledger". For payments it is not.

**Recommendation.** This needs a decision record, not a patch: *who may go into
debt.* The smallest rule that closes it is a floor of zero for an identity that
is not enrolled, where "enrolled" is a predicate every replica derives from the
log (for example: named in the genesis charter, or vouched for by an established
member or founder). The same predicate should gate certificate issuance. Such a
key can still receive, and spend what it holds.

### RRN-A-017 · High — Established standing can be manufactured in one settlement window

**Where:** `rrn-reputation/src/context.rs:202-221`, `:252-269`, `:427-438`,
`:454-482`, `rrn-reputation/src/snapshot.rs:84-94`,
`rrn-ledger/src/engine.rs:171-254`, `rrn-station/src/core.rs:4599-4636`,
`:5860-5889`, `rrn-dispute/src/sortition.rs:142-161`.

Four properties combine:

1. A payment from an address to itself is admitted, and scoring counts it as a
   trade for the sender and its confirmation as an attestation for the
   confirmer.
2. Ten such one-centicommon self-payments give a raw composite of 2.75 — above
   the Member band (2.0) — once they settle, 24 hours later. The ADR-0009
   velocity limit that the threat model describes as a cap ("a fake identity
   needs ten weeks") is, in code, a log line.
3. Never-enrolled keys can do the same over the delay-tolerant door (RRN-A-016).
4. An anchoring voucher is judged on its *raw* composite, so a member who did
   step 2 can anchor others without being anchored.

One paired member self-pays ten times, has three fresh keys do the same in a
bundle, and vouches for the three. A day later the community has three
"established members", none of them a person. Bootstrap grace ends by itself at
three (ADR-0015), so the founders leave the governing electorate and the jury
pool. The three keys *are* the electorate: governance records are routable over
the delay-tolerant door, so they can co-sign, vote and amend the charter. Every
honest member below the band is refused Tier-2 confirmations. The jury pool for
the attacker's own disputes is the attacker's keys (recusal removes those who
vouched *for* a party, not those the party vouched for).

**Reproduced.** Four bundles of ten self-payments and confirmations, all
admitted; each key's raw composite 2.748; after the vouches,
`established_members` returns exactly the three throwaway keys and `in_grace` is
false.

**Recommendation.** With RRN-A-016's enrollment decision: refuse a proposal
whose sender is its receiver; count trade and attestation events per distinct
counterparty; enforce the velocity limit in the scorer rather than logging it;
require an anchoring voucher to be established (or reachable from the founders);
recuse a party's vouchees as well as its vouchers. Several of these change the
ADR-0009 formula, which is locked — they need a new ADR.

### RRN-A-018 · Medium — A refusal can be planted in the receipt cache for someone else's record

**Where:** `rrn-station/src/core.rs:4406-4421`, `rrn-storage/src/dtn.rs:293-323`,
`:338-358`, `rrn-cli/src/wallet.rs:1546-1550`, `:1690-1727`.

Bundle ingest is idempotent through a cache keyed on the Blake3 of the ordered
*record hashes*, consulted before any signature is checked. A record hash covers
the record's bytes, not the entry's author or signature. Anyone who has seen a
record — a courier, the counterparty of an offline spend, someone who
photographed a sheet — can present it under a junk outer signature. The station
answers `bad-signature`, signs that receipt, and caches it under the same key an
honest presentation of that record would have. The honest bundle then gets the
cached refusal verbatim and is never validated. `rrn wallet` treats a refusal as
final, drops the row from its outbox, and reports a later different answer as a
conflict.

The same cache makes order-dependent refusals permanent with no attacker at all:
a confirmation that arrives before its proposal is cached `not-proposed` for
that presentation forever, and a courier holding two members' bundles chooses
which lands first. The glossary's "a courier needs no trust" does not hold
against this.

**Reproduced.** Forged presentation → `Refused{BadSignature}`; the genuine
presentation afterwards → the same `Refused{BadSignature}`; nothing admitted.

**Recommendation.** Key the cache on the entry envelopes; never serve a cached
receipt containing an outcome that could differ on re-presentation (only
`admitted` and `known` are stable); have wallets treat the transient slugs as
retryable; file delivery rows under the record's signer. The threat model,
`sms-carrier.md` §6 and the red-team "Duplicate" row currently call re-issue
"harmless by design".

### RRN-A-019 · Medium — A certificate-backed spend can be voided by its signer, unprovably

**Where:** `rrn-ledger/src/engine.rs:122-126`, `:194-199`, `:221-228`, `:239-241`,
`rrn-station/src/core.rs:4735-4750`, `rrn-mobile-ffi/src/cert.rs:331-343`.

ADR-0021's bargain is that an offline receiver can rely on a certificate-backed
spend because the headroom was escrowed at issuance, and that a spender who
cheats "must be *provably* dishonest". The engine, however, applies three checks
the spender controls *before* the certificate cap is ever examined, and records
equivocation only for two later outcomes (`CertificateOverspent`,
`CertificateExpired`):

- **Return the certificate.** A `CertificateReturn` rides a bundle and needs no
  nonce. Every spend against a returned certificate is refused
  `CertificateNotOutstanding` — including several that jointly exceed the cap.
  The signed certificate still verifies offline for its whole validity.
- **Burn the nonce.** Submit any other record at the spend's nonce first (a
  payment request needs no floor check); the spend fails the nonce check.
- **Window games.** A future `proposed_at`, or an `expires_at` seconds away,
  passes the receiver's check (`offline_spend_verify` compares neither to the
  clock nor to the certificate's expiry) and fails the station's.

In each case the receiver handed over goods against a spend that verified, the
station refuses it with an ordinary slug, and nothing is recorded: no proof, no
reputation effect, no bar on the next certificate. Loss per receiver is still
bounded by the cap; what fails is provability and "once per member".

**Recommendation.** Tighten the receiver-side verifier to mirror the station
(future-dating, an expiry floor at the certificate's expiry, a nonce collision
in the presented history). On the station, a dated clarification to ADR-0021 and
ADR-0025: a member-signed spend together with a member-signed return of the same
certificate, or with a different admitted record at the same nonce, is
equivocation-class evidence; both halves are member-signed, so the proof is
self-contained.

### RRN-A-020 · Medium — The debt floor reads a balance cache that is never reconciled

**Where:** `rrn-ledger/src/engine.rs:74-92`, `rrn-ledger/src/settlement.rs:254-256`,
`:273-320`, `rrn-station/src/core.rs:2817-2828`, `rrn-station/src/ledger_view.rs:44-93`.

There are two balances. The one members see (`rrn balance`, the phone) is folded
from the log: station-pinned settlements plus contract charges. The one the debt
floor reads is the `balances` table, written only by `Settler::apply_balance`.
Contract charges are appended to the log and never touch that table. So:

- a buyer whose real balance is −200.00 from contract charges still has the full
  −20.00 of headroom and can still be issued certificates;
- a provider shown +30.00 from subscriptions is refused a 25.00 spend;
- a crash between the settlement append and the two cache writes leaves the
  cache short of that settlement forever, because settling an already-settled
  transaction is a no-op.

Nothing rebuilds the table. `rrn-storage::replay` is not called outside its own
crate; startup opens the database and runs migrations. The threat model
("a tampered derived row … is overwritten by replay"), ADR-0005 ("recoverable by
replay") and the repository's own rule that caches are caches all say otherwise.

**Recommendation.** Derive the settled balance inside `LedgerSnapshot` and have
the floor read that; retire the table or rebuild it at startup.

### RRN-A-021 · Medium — Jury verdicts and escalation ballots are windowed on the voter's own timestamp

**Where:** `rrn-dispute/src/resolution.rs:100-131`, `:216-233`,
`rrn-dispute/src/verdict.rs:87-102`, `rrn-dispute/src/panel.rs:110-168`,
`rrn-dispute/src/escalation.rs:286-288`; contrast `equivocation.rs:594-626`.

`append_verdict` accepts a verdict whose `cast_at` is not after `now` and falls
inside the resolution window, then re-derives the panel *as of `cast_at`*. The
tally later credits a verdict by the same signed time. A juror who let their
response window lapse and was replaced can therefore sign a verdict dated inside
their old window days later: it is admitted, they are retroactively never
redrawn, the replacement's verdict becomes inert, and the ruling can flip. The
ruling time is computed from cast times too, so the appeal window can already be
closed when the flip lands. Two jurors can erase an appeal window the same way.

The equivocation-jury path fixed exactly this and names the attack in a comment;
the ordinary path was not changed, and the threat model says no per-member
timestamp reaches this arithmetic.

**Recommendation.** Read the entry's admission time for seating and windows on
both paths; keep `cast_at` as testimony.

### RRN-A-022 · Medium — Any settled payment naming a listing consumes its stock

**Where:** `rrn-station/src/core.rs:2443-2515`, `rrn-marketplace/src/lifecycle.rs:747-762`,
`:891-918`.

A proposal may carry a `listing_id`. When it settles, the station signs a
`StockConsumed` for that listing if the listing is active and tracks stock.
Nothing checks that the payment's receiver is the listing's provider or that the
amount relates to its price. A member pays themselves one centicommon *n* times
naming a competitor's listing, and the station attests *n* sales: the listing
reads sold out and leaves the index.

**Recommendation.** Require the receiver to be the listing's provider and the
amount positive; preferably require an agreed inquiry for that buyer and price.

### RRN-A-023 · Medium — The pairing code is 32 bits over two static keys with no commitment

**Where:** `rrn-station/src/paired.rs:161-168`, `rrn-station/src/pairing.rs:117-124`,
`rrn-station/src/core.rs:5462-5495`, `:6664-6686`. Station half of the mobile
finding RRN-M-001 (August), which is still open.

The code both sides compare is the first eight hex characters of a hash of the
station's and the phone's long-term public keys. The phone's request does not
name the station it is for. A party on the pairing LAN who chooses its own key
after seeing the other's can search about 2^32 candidates offline for a key
whose code equals the genuine one, and can forward the phone's request unchanged
to the real station so that the operator's list shows the genuine code. The
symmetric case puts a second pending entry with the right code in the operator's
list, which the operator confirms by address.

The threat model and the red-team checklist say a man-in-the-middle "would have
to present its own key, which changes the code". That holds only against an
attacker who does not search. A short code is sound with commit-then-reveal or
committed fresh randomness; this handshake has neither.

**Recommendation.** Bind the intended station key into the request's signed
bytes, and either lengthen the code substantially or add a commitment round.
This is a wire change shared with the phone and with `rrn wallet`, and wants an
ADR-0008 clarification.

### RRN-A-024 · Medium — Channel responses are bound to neither the recipient nor the request

**Where:** `rrn-station/src/rpc_envelope.rs:183-194`, `:267-271`,
`rrn-station/src/paired.rs:101-112`, `rrn-station/src/channel_client.rs:238-244`.
Supersedes RRN-A-010.

The station signs `{v, nonce, result | error}`. The request binds its recipient
inside the signed bytes; the response names no member, no method and no request.
Per-member nonces are small integers that all start at one, and re-pairing
resets both sides. Consequently a station-signed reply issued to one member
verifies as the reply to another member's request with the same nonce, and every
reply recorded before a re-pair (or a restore of the same key) verifies again
afterwards. A paired member who can intercept LAN traffic — the channel is plain
HTTP by design — can answer a victim's write with a recorded success, so the
app reports a dispute as raised or a payment as sent when the station never saw
it.

August rated this Info on the premise that nonce state never resets without
re-pairing; re-pairing with unchanged keys is exactly where it breaks.

**Recommendation.** Add the hash of the request payload to the response
envelope and check it in both clients.

### RRN-A-025 · Medium — The peer port serves the whole log to anyone, without bounds

**Where:** `rrn-station/src/gossip.rs:214-273`, `rrn-storage/src/log.rs:363-412`,
`rrn-station/src/rpc_client.rs:30-39`. RRN-A-003 (August) is still open.

The writer/replica split closed the *tampering* half of the August finding: a
writer never pulls. The serving half is unchanged. Any host that can reach
`[network] listen` gets the entire log — the vouch graph, every memo, every
dispute statement — with no authentication and no allowlist. Two availability
problems sit beside it: a connection that never sends a newline grows a buffer
without limit, and every `log_range`, even for one entry, loads every row from
the requested position to the tail on the core thread.

The runbook says the port "should stay unreachable from other machines" and,
fifteen lines later, tells the operator to point a replica at it over the LAN
for an off-site copy, without saying what that exposes. The disclosure is still
absent from the threat model.

**Recommendation.** Cap the request line on this port, on the local socket and
in the replica client; page `log_range` with a SQL upper bound; serve only
configured replica addresses until Phase 3 authenticates peers; state the
disclosure in the threat model and the runbook.

### RRN-A-026 · Medium — `rrn paper show` reports "signature ok" for any signer

**Where:** `rrn-cli/src/paper.rs:472-644`; `docs/community-setup.md:937-940`;
`docs/spec/qr-payloads.md:221-223`; `docs/threat-model.md:3457-3464`.

The runbook tells a receiver to check an offline spend voucher with `rrn paper
show` before handing over goods, and says the command verifies that the
certificate is station-signed, belongs to the payer, fits the remaining cap and
is unexpired. The command checks that each signature is *self-consistent*. A
certificate signed by a throwaway key prints "signature ok"; a proposal signed
by anyone, naming a real certificate holder as sender, prints "signature ok";
there is no check of the certificate id, the receiver, the cap or expiry, and
the history is only counted. A receipt prints "station signature ok" when the
signer equals the station the receipt itself names. JSON mode says
`"verified": true`.

The phone app has no certificate screens, so in a pilot this is the receiver's
only tool. The mobile FFI's `offline_spend_verify` does do these checks; the CLI
shares none of it. The threat model says the unpinned-signer limit "is stated in
the command output". It is not.

**Recommendation.** One verifier in `rrn-ledger`, called by the FFI and the CLI;
a `--station` pin on `paper show`; without the pin, output that says the signer
was not checked and `"verified": false`.

### RRN-A-027 · Medium — `rrn wallet confirm` signs from a bare id

**Where:** `rrn-cli/src/wallet.rs:1232-1247`; `rrn-ledger/src/engine.rs:242-248`,
`:317-324`.

A negative-amount proposal is a payment request: it debits its *receiver*, and
the receiver's confirmation is their commitment (ADR-0018). `rrn wallet confirm
<tx_id>` builds and signs a confirmation from the hex id alone — it holds no
copy of the proposal, fetches nothing, and shows no amount, direction or
counterparty. A member told "I paid you five Commons, confirm this id" signs a
debit against themselves up to the Tier-2 ceiling. Offline, which is the mode
this wallet exists for, they could not have checked. The companion mobile report
records the same confusion on the phone (RRN-M-012).

**Recommendation.** `confirm` acts only on a proposal it has verified (fetched
online, or supplied as a file offline), prints who pays whom, and requires an
explicit flag to confirm a debit against the member.

### RRN-A-028 · Medium — Restoring a whole-directory wallet backup forks the member's chain

**Where:** `rrn-cli/src/wallet.rs:513-528`, `:812-816`, `:826-834`;
`rrn-station/src/core.rs:4486-4520`; `docs/community-setup.md:344-351`.

ADR-0028's no-self-fork rule is enforced by a `chain_state` flag that only
`init --restore` and `recover` set to `unknown`. The runbook tells members to
back up the *whole wallet directory*. A member who restores such a copy after
transacting further has a wallet that reads `anchored` at an old position; the
next `pay` signs at a position the station already holds a different entry for.
That is an outbox fork: the station records provable equivocation, zeroes both
reputation dimensions and opens a jury case — against a member who followed the
documentation. The one command that would notice, `sync`, fails first, because
the transport nonce rolled back with the directory and the station rejects it;
the wallet prints "not paired".

**Recommendation.** Detect a copied or rolled-back home (an instance marker
checked at open) and land it in `unknown`; give `sync` a truthful message for a
stale nonce; correct the runbook and ADR-0028's "honest paths no longer lead
into an equivocation record".

### RRN-A-029 · Medium — The recovery-ceremony fingerprint is 40 bits of a bare key hash

**Where:** `rrn-identity/src/recovery/ceremony.rs:62-68`; surfaced through
`rrn-mobile-ffi/src/recovery.rs:215-223` and `rrn-cli/src/wallet.rs:645-650`.

The fingerprint added in September to close RRN-A-001's second recommendation is
ten hex characters of a hash over the request's ephemeral public key. It is the
only control when a recovery request is relayed rather than scanned in person —
which the CLI ("or paste this line to each holder") and the app ("in person or
on a call") both invite. The genuine request is visible before the attacker
chooses a key, there is no commitment, and matching 40 bits is a search of about
10^12 key derivations: reachable with rented compute inside the hours-to-days a
ceremony stays open. A substituted request then shows holders the same code the
owner reads aloud, and each holder seals their share to the attacker.

**Recommendation.** At least 80 bits, over the tag, the recovery key and the
target address, rendered for reading aloud; or state the bound and restrict the
normative procedure to in-person scanning. Changes a published fixture and
ADR-0016's text.

### RRN-A-030 · Medium — The boot-ceremony console fingerprint can never match the phone's

**Where:** `rrn-station/src/storage/vmk.rs:363-375`, `rrn-station/src/main.rs:332`,
`:386`; `rrn-identity/src/recovery/ceremony.rs:62-68`;
`docs/spec/vmk-boot-ceremony.md`.

Under the encrypted profile the unlock ceremony is wallet-free, and the console
fingerprint is its only authenticator (ADR-0024). `station unlock` prints one
algorithm: uppercase base32 over the recovery key and the volume key's public
key. The request it emits is an ordinary recovery request, and every holder's
phone now shows the *other* algorithm (RRN-A-029's) under "Ceremony fingerprint
— it must match their screen exactly". The two can never be equal. A legitimate
unlock always mismatches: holders who follow the rule cannot unlock the station,
and holders who learn to ignore the mismatch will respond to a seizer's forged
request for the same volume, which is the attack the fingerprint exists to stop.

The specification says the mobile client "must reproduce" the console algorithm
before the check can be relied on. It does not note that the shipped client now
shows a different code for the same request.

**Recommendation.** One algorithm for every ceremony, fixed together with
RRN-A-029.

### RRN-A-031 · Medium — Lost-passphrase restore accepts an archive anyone can forge

**Where:** `rrn-identity/src/envelope.rs:158`, `:197-206`;
`rrn-station/src/backup.rs:202-260`; `rrn-station/src/recovery.rs:252-304`;
`rrn-station/src/reticulum.rs:130-141`.

A backup archive wraps its data key twice: under the passphrase, and in an
anonymous sealed box to the station's public key. The second wrap authenticates
nobody — anyone who knows the station's address can build an archive that opens
under the station's secret key. `station recovery restore --from-backup` uses
that path. Someone who can replace the archive where it is kept (the runbook
calls archives "safe to copy anywhere convenient") waits for a total-loss
recovery; the holders' ceremony reconstructs the real key, the forged archive
opens cleanly, and every file in it except the wallet is written to the data
directory with no allow-list: the ledger, the paired-device list, `config.toml`,
and any extra file. Nothing verifies the restored chain. The restored config
names the executables the daemon spawns for the radio adapter, which is code
execution as the station user while the wallet is decrypted.

The August report recorded "a tampered archive fails closed … no action"; that
holds for a modified genuine archive and for the passphrase path, not for a
substituted archive on this one.

**Recommendation.** A station-signed manifest inside the bundle, verified on
both restore paths; an allow-list of file names; never adopt a restored config
on the recovery path without the operator's confirmation; verify the chain after
any restore.

### RRN-A-032 · Medium — Encrypted profile: the passphrase that opens every backup sits on the unencrypted root

**Where:** `docs/community-setup.md:219-223`, `:619`, `:714-719`;
`rrn-station/src/backup.rs:147`; ADR-0024 lines 110-116.

ADR-0024 moves the wallet inside the encrypted container so that there is "no
station passphrase on the plaintext boot medium". The daemon still needs the
passphrase to run, and the runbook's unit file — which the encrypted-profile
section tells operators to use — reads it from `/etc/railroad/station.env` on
the unencrypted root. Every backup archive is sealed under that same passphrase,
and the runbook has the operator write one to the node's own disk before
migrating. A seized powered-off disk plus any archive (the same disk, or the USB
stick taken in the same raid) yields the full ledger and the wallet file, which
that passphrase also opens: the station's signing key, with no member quorum
involved.

**Recommendation.** Under the encrypted profile keep the passphrase inside the
container or prompt for it after unlock; have `station backup` refuse an output
path on the boot filesystem; correct the runbook.

### RRN-A-033 · Medium — A charter amendment's replacement charter is neither validated nor shown

**Where:** `rrn-governance/src/proposal.rs:263-290`; `rrn-governance/src/tally.rs:149-161`,
`:234-250`; `rrn-station/src/governance_view.rs:73-114`.

`Proposal::validate` checks an amendment's title, body and voting mechanism.
Nothing else in the replacement charter is bounded, and the proposal views the
operator and the phones read carry the title and body but not the charter being
voted in. Voters approve prose. The charter they enact may set an approval
percentage of zero (the test is `yes × 100 ≥ pct × decisive`, so a later
proposal passes with no yes votes), a percentage above one hundred (nothing
passes again), an implementation delay of zero (later amendments are recorded as
enacted and never take effect), or a different founder set — which the tally and
the dispute pool read from the effective charter while eligibility reads the
root's.

No shipped tool can author an amendment, so every one arrives hand-built.

**Recommendation.** Bound every field of a replacement charter in `validate`,
require the founder set unchanged (as ADR-0012 and ADR-0015 already say), and
expose the replacement charter or a field diff wherever a proposal is shown.

### RRN-A-034 · Medium — Concluded outcomes are re-judged under the current charter

**Where:** `rrn-governance/src/tally.rs:103-111`; `rrn-governance/src/lifecycle.rs:34-66`;
`rrn-governance/src/statute.rs:152`, `:213`.

`tally` resolves thresholds from today's effective charter. `enact_due` re-runs
it every hour for every proposal that was never implemented, with no age bound.
A statute that failed last quarter at 40% under a 50% bar is enacted by the
sweep, with no new vote, the hour after an amendment lowers the bar to 40%.
Raising a bar silently removes statutes from the in-force set the same way. The
window attestation records which charter was in force when a proposal opened;
nothing reads it.

**Recommendation.** Judge a proposal under the charter in force at its open
position; never enact one whose window closed with a failed outcome.

### RRN-A-035 · Medium — Governance derivation is quadratic in proposals on the core thread

**Where:** `rrn-governance/src/proposal.rs:448-460`, `:595-641`;
`rrn-governance/src/tally.rs:103-111`; `rrn-governance/src/lifecycle.rs:34-66`;
`rrn-station/src/governance_view.rs:199-306`.

Each eligibility check builds a fresh scoring context (two to three passes over
the log). Listing proposals does one per proposal. Every tally re-resolves the
effective charter, which lists proposals. The hourly sweep tallies every
unimplemented proposal, including ones that failed long ago or never gathered a
co-signature. The cost per sweep, and per `governance_proposals` read from any
phone, is on the order of P² log replays, on the thread that serves everything.
One established member who submits a few hundred un-co-signed statutes makes the
writer spend most of each hour replaying, and the log is append-only, so there
is no operator remedy. The call structure is confirmed; the wall-clock figure is
an estimate and was not measured.

The threat model accepts "no rate limit" and "O(N) replay" as an attention cost.

**Recommendation.** One charter resolution and one scoring context per position
per request; drop concluded proposals from the loop; cap open unpublished
proposals per author.

### RRN-A-036 · Medium — Forged frames can pin the station's economic airtime

**Where:** `rrn-station/src/dtn_sync.rs:325-399`, `:528-620`;
`rrn-station/src/dtn_loop.rs:153-167`; `rrn-protocol/src/framing.rs:326-333`;
`scripts/reticulum/lxmf_adapter.py:87-131`.

With the radio sidecar enabled, any node that can deliver a message to the
station's destination can open up to 64 partial payloads, each tracked for seven
days. For each, the station enqueues a request-for-missing-chunks every 30
seconds at *economic* priority — the class the design says is never starved. At
the default budget (250 B/s at a 1% duty cycle) that queue is hours long, and
governance and bulk traffic never drain behind it. Every decodable bundle from
any source also earns a receipt at economic priority, re-sent every 30 seconds
for a day, from a cache with no size cap. Budget is deducted even when the
adapter silently drops a frame to an unknown identity, so a spoofed source
starves honest traffic with the radio silent.

**Recommendation.** A separate small budget for control frames and unsolicited
receipts; backoff and a retry cap per payload; a short lifetime for live
partials; a cap on the outbound cache.

### RRN-A-037 · Medium — Unbounded permanent writes, including from never-enrolled keys

**Where:** `rrn-protocol/src/binding.rs:92-109`, `:170-180`;
`rrn-station/src/core.rs:4453-4463`, `:4779-4874`, `:5860-5889`;
`rrn-identity/src/vouch.rs:37-46`; `rrn-marketplace/src/contract.rs:147`;
`rrn-governance/src/proposal.rs:161-171`; `rrn-governance/src/emergency.rs:161-187`.

Phase 2's threat model says it "bounded the *size* of every input". Several
fields that land in the permanent, fully-replayed log are bounded only by the
transport: a transport binding's `destination` (an unvalidated string of up to
megabytes, self-signed by *any* key and appended verbatim), a vouch's statement
and community (the community is never compared to the station's), a contract's
free-form metrics map, an administrative rule's scope, an emergency
declaration's reason and scope (echoed in every `whoami`), and every string in

**Recommendation.** Size and format bounds at admission for each field (a

### RRN-A-038 · Low — Unchecked arithmetic on caller-supplied integers; no panic containment

`core.rs:5466` and `:5550` subtract a caller's timestamp from the clock and take
the absolute value; `events.rs:121` adds one to a caller's cursor;
`rrn-marketplace/src/inquiry.rs:546` and `contract.rs:490`, `:503` do arithmetic
on party timestamps. The workspace has no `[profile.release]` section, so a
release build wraps silently, while a debug build — which the README's build
line and the seizure drill script produce — panics the core thread, with the
consequence in RRN-A-013. Use checked or saturating arithmetic, and consider
`overflow-checks = true` for release.

**Update (2026-10-09, PR #76) — daemon side fixed.** The two skew checks
(`core.rs`, pairing and channel envelopes) use saturating subtraction and
absolute value; the event cursor uses a saturating increment, and the log
iterator now treats a cursor past `i64::MAX` as empty rather than wrapping it
negative into a whole-log read; the channel frame-length sums use checked
addition. Core panic containment is described under RRN-A-013. Release builds
now set `overflow-checks = true`. The marketplace timestamp arithmetic
(`inquiry.rs`, `contract.rs`) is fixed separately, with the RRN-A-014/015
marketplace work.

**Update (2026-10-09, PR #77) — marketplace side fixed.** An inquiry's
staleness check saturates (`is_stale`), and a contract's due times, natural end,
and termination effective time use saturating arithmetic on the admission
anchor rather than on party timestamps.

### RRN-A-039 · Low — Pairing table, long-poll and reputation reads are unbounded per caller

The pending-pairing map is pruned by age only, so anyone can fill the operator's
confirmation list at the rate the core can verify signatures; a captured request
can be re-presented for five minutes; and confirming an already-paired address
resets its nonce high-water mark. Each parked `/subscribe` runs a full ledger
derivation on every log append, with no per-member cap. `reputation_band` for an
address that was never seen forces a full scoring replay and persists a snapshot
row for it.

### RRN-A-040 · Low — Any paired member reads any member's ledger view and every dispute

RRN-A-004 (August) is unchanged, and wider: besides `balance`, `transactions`
and `next_nonce` for an arbitrary address, any paired device can read every
dispute's reason, responses, seated jurors and live per-juror verdicts — so a
late juror sees how the others voted. No transparency policy is recorded in the
threat model or the runbook. Scope the reads to the caller, or write the policy
down so a pilot community can be told.

### RRN-A-041 · Low — Contract notice and start run on party timestamps; charges bypass the tier gate

A termination's `requested_at` is the signer's own clock and is not bounded, so
a back-dated termination ends a contract with no notice served and no penalty; a
far-future `started_at` gives a contract that reads active and never charges. A
single contract charge may move 50 Commons or more, which ADR-0011 says is
blocked. Separately, an inquiry's admission is re-decided on every read against
the current reputation cache: a buyer whose standing dips makes the inquiry and
its contract vanish, and charges resume as a backlog when it returns.

**Update (2026-10-09, PR #77) — contract parts fixed.** A contract's schedule
and a termination's notice now run from their admission (ADR-0022), so neither a
back-dated `requested_at` nor a far-future `started_at` moves them; both stay in
the signed records as testimony. A per-period amount and an early-termination
penalty are both held under the Tier-3 floor in the validators, so no single
contract charge can move a Tier-3 amount. **Still open:** an inquiry's (and so
its contract's) validity is still re-derived against the current reputation
cache on every read.

### RRN-A-042 · Low — Equivocation cases cannot be ruled on by anyone

`append_equivocation_ballot` and `append_equivocation_reseat` are called only
from tests. No operator command, channel method or bundle route reaches them, so
every equivocation case lapses and its penalty — both reputation dimensions
zeroed, certificates blocked — has no route to an Overturn. The threat model
says the operator wallet "is the juror that can act".

### RRN-A-043 · Low — Governance edge cases

- **Deadlock at exactly three established members.** Outside grace the co-sign
  threshold is fixed at three and an author cannot co-sign, so with three
  established members nothing can publish — at the same instant the founders
  lose their seat.
- **The charter freeze is strict at the activation instant.** While the station
  clock sits at or behind an emergency's activation instant, admissions are
  stamped with that instant and read as ungoverned. ADR-0023 accepts a one-tick
  edge; the code comments and the threat model claim a regressed clock cannot
  slip a charter past the freeze.
- **`governance_charter_sign` signs an opaque blob.** It checks only that the
  bytes decode as a charter, whose decoder ignores unknown keys and whose body
  carries no `kind`; the CLI never shows what was signed. No injection into an
  honest writer was found.
- **A declaration can dead-end silently** when the electorate shrinks while
  signatures gather: later co-signatures are admitted and nothing activates.

### RRN-A-044 · Low — `rrn wallet`: certificate history, recovery ordering, phone-origin keys, passphrase handling

- Certificate spend history lives only in the wallet. After a restore, a
  re-imported certificate shows its full cap and the wallet permits an
  overspend, which the station records as equivocation.
- `recover --force` deletes the existing wallet and outbox before the
  replacement is durable; a failed passphrase prompt loses both.
- A key that lived on a phone cannot be made to sign in the CLI wallet: a phone
  export restores without the member metadata the wallet requires, and
  `recover` leaves the chain `unknown` forever when the station has no outbox
  head for that key (a phone submits over the live channel and never creates
  one). ADR-0028 and the ADR-0016 clarification present both as supported.
- The runbook's `export RRN_WALLET_PASSPHRASE='…'` puts the passphrase in shell
  history beside the wallet file; an empty passphrase is accepted at `init`; the
  passphrase string is not zeroized.

### RRN-A-045 · Low — CLI text output does not neutralize control characters

Memos, listing titles and descriptions, proposal bodies, dispute statements,
inquiry messages, contract metrics and scanned QR fields are printed verbatim in
text mode. A memo containing a newline fabricates a row in the operator's
`rrn transactions`; escape sequences can rewrite earlier lines. JSON mode is
safe. One sanitizing function at every text sink closes it.

### RRN-A-046 · Low — File and directory modes; socket and provisioning windows

RRN-A-006 (August) is still open: the wallet's temp file is created and then
chmod'ed, and the backup archive, recovery packages and the paired-device list
are written at the default mode. Beyond it: the data directory and the mounted
state directory are `0755`; the local socket is bound and then chmod'ed; and
during the one-time migration to the encrypted profile the container file is
world-readable and the throwaway keyslot passphrase is a world-readable file in
a world-searchable directory under `/dev/shm` (falling back to `/tmp`), so a
local process that copies both in that window can derive the volume key, which
never rotates. Set a restrictive umask at start and create private files with
their mode.

### RRN-A-047 · Low — Restore is unverified and non-atomic; the chain is still never verified at runtime

RRN-A-005 (August) is still open: `verify_chain` runs only inside the migration
to the encrypted profile. Neither startup nor either restore path calls it; it
checks hashes, not signatures or sequence contiguity; and an entry's admission
time is outside the hash chain. Restore also overwrites the database in place
without removing stale `-wal`/`-shm` files, leaves a half-restored directory on
failure, and writes the wallet at the default mode.

### RRN-A-048 · Low — The wallet passphrase is inherited by the radio sidecar; the adapter does not authenticate senders

Neither child spawn clears the environment, so `rnsd` and the Python adapter —
third-party code parsing radio input — hold `RRN_PASSPHRASE` and can read the
wallet file as the same user. The threat model's limit on a carrier compromise
("the wallet file is passphrase-encrypted at rest") does not survive that. The
adapter also forwards messages without checking that the transport validated the
sender's signature, so the source endpoint the station correlates receipts and
control frames by can be claimed by anyone (*Plausible*: inferred from the
adapter code; the library was not run).

### RRN-A-049 · Low — Encrypted profile: plaintext outside the container

SQLite's temporary storage defaults to files, so large sorts and statement
journals spill to `/var/tmp` or `/tmp` on the unencrypted root. The check for
plaintext left behind by the migration covers four fixed file names and misses
an interrupted backup's snapshot directory, which is a full plaintext ledger. A
missing `config.toml` beside an encrypted container silently means the
plaintext profile.

### RRN-A-050 · Low — Identity hardening

- `Address::from_str` accepts non-zero bech32m padding bits, so each key has
  sixteen valid spellings; string-keyed duplicate checks (the phone's holder and
  recipient guards) are bypassed, and `RecoveryPackage::create` does not reject
  a duplicate holder key.
- A recovery shard payload is unauthenticated, and a holder's device cannot test
  that a shard is addressed to it or opens.
- `RecoverySession` accepts share indices above the split cap, which reallocates
  and frees a buffer holding genuine shares without wiping it.
- Wallet KDF costs are read unclamped from the file; import paths now exist, so
  a hostile file can demand unbounded memory or time.
- Zeroization gaps in the wallet's CBOR encode/decode, the envelope's error
  path and the FFI passphrase strings.
- The "no `unsafe`" rule is a per-crate attribute, not a workspace lint, and
  `rrn-dispute` lacks it. No `unsafe` exists there today.

### RRN-A-051 · Low — Storage hardening

Receipt-delivery rows are keyed by record hash alone and filed under whichever
author first presents the record, so the real author's receipt fetch can come up
empty. The log's content hash excludes the signer, and both replica dedup and
the bundle "already known" answer key on it. `AppendLog::append` reads the tail
before opening its write transaction, and nothing stops a second daemon on the
same data directory (`bind` removes a live socket file).

### RRN-A-052 · Low — Supply chain and CI

- Both repositories' default workflow token is write-scoped and may approve pull
  requests; the workflows declare no top-level `permissions`; third-party
  actions are pinned by mutable tag. A compromised action tag would run with a
  write token on `main`.
- `main` has no branch protection or ruleset in any of the three repositories.
  Dependabot security updates and secret scanning are disabled.
- RRN-A-008 (August) is still open: `lru 0.16.4` (RUSTSEC-2026-0253, unsound)
  through `tantivy`; fixed releases exist. `cargo audit` and `cargo deny` are
  otherwise clean, with `paste` (unmaintained, via `dcbor`) allowed.
- The Reticulum pins (`rns==1.5.2`, `lxmf==1.1.1`) are by version, not hash.
- Nothing in `rrn-protocol` or `rrn-mobile-ffi` has a fuzz target, though both
  decode bytes from couriers, radios and QR codes; the address and round-trip
  targets assert no property beyond "does not panic".

### RRN-A-053 · Info — Smaller observations

- Replay trusts append-time verification for member-signed ledger kinds, and the
  dispute readers do not re-check a verdict's or ballot's envelope signer.
  Unreachable on a writer, which admits only through the engine; relevant to a
  tampered or restored database (RRN-A-047).
- `Engine::cancel_proposal` has no caller outside tests: an expired proposal
  stays `Proposed` forever. Harmless to the floor; contrary to the documented
  lifecycle.
- An outbox-fork equivocation is avoidable by the equivocator, since a record's
  signer need not be the entry's author. The certificate cap, not the fork, is
  the real double-spend defense.
- An escalation tie upholds the dispute, voiding the confirmed transfer;
  ADR-0014 does not state the tie rule.
- The portable reputation export omits dispute and equivocation records, so a
  verifier derives a cleaner profile than the exporter held. No caller today;
  matters for Phase 3.
- Governance party timestamps are never refused when future-dated, though
  ADR-0022 §3 requires it; the proposal view labels the author's `created_at`
  as the start of the window.
- `now_secs()` still falls back to zero on a pre-epoch clock (RRN-A-012). The
  admission clamp now prevents it reordering a non-empty log.
- A parked `/subscribe` keeps being served for up to 30 seconds after its device
  is unpaired.
- X25519 contributory behavior is still unchecked (RRN-A-009). Re-evaluated for
  the ceremony, where shares are sealed to a key taken from an unauthenticated
  request: only the request's author chooses that key, so there is no added
  power.

## What was checked and found sound

Recorded so the next reviewer does not re-derive it. Each item was verified in
the file named.

- **Signature discipline.** `verify_strict` everywhere; `MultiSignedPayload`
  rejects count mismatch and duplicate signers before verifying; every append
  path verifies before inserting (`log.rs` `append`, `append_raw`,
  `LogBatch::append`); no `unsafe` anywhere under `crates/`.
- **Decode boundaries.** `CBOR::try_from_data` has exactly one call site, inside
  the depth-guarded `checked_from_data`; the pre-scan agrees with the decoder at
  every early return; dCBOR pre-allocates nothing attacker-sized. Typed decoders
  check `kind` and recompute content ids.
- **Station-signed kinds are pinned on replay**, and a mismatch is skipped, at
  every reader found: settlement, cancellation, certificate, equivocation and
  its verdict (`LedgerSnapshot`), `ledger_view::balance_of`, events, history,
  contract-charge accounting, and all five governance attestation kinds. The
  threat model's "one signer-pin gap that remains" and the red-team residual 6
  are stale — the docs under-claim here.
- **The channel.** Envelope order is seal-open, signature over the exact
  received bytes, recipient equals the station, paired, skew, strictly greater
  nonce, persisted before dispatch. Every channel write compares the record's
  signer to the authenticated device. No operator-only method is on the mobile
  allowlist. Pre-authentication error strings are constants. Inquiry and
  contract reads are party-scoped and answer non-parties as "not found".
- **Writer and replica.** A writer refuses `append_entries` and refuses to start
  with peers; a replica refuses bundle ingest and channel writes and runs no
  sweeps.
- **Bundle ingest.** Size and entry caps before parsing; no double admission;
  the kind allowlist is closed (certificate requests, vouches, verdicts, ballots
  and marketplace kinds are unroutable); the Tier-2 stake gate and governance
  guards are shared by all three admission paths; nobody can cause an
  equivocation record against an honest member, since a fork needs two entries
  signed by the author and evidence is re-verified.
- **Framing and paper codecs.** CRC before any state is touched; chunk, payload
  and in-flight bounds; per-chunk caps before base64 decode; no reachable panic
  found on scanned or received bytes.
- **Ledger arithmetic.** Saturating throughout `rrn-ledger`; Tier 3 and above is
  refused, never clamped; the committed-position and certificate-reservation
  accounting has no double count and releases at one shared boundary;
  conservation holds for the log-derived fold.
- **Governance.** Electorates, co-signer and voter eligibility and the quorum
  denominator are pinned at the window attestation's position; one key one vote
  on write and on replay; every path ends in the same append guards; emergency
  activation, refusal, anchor and expiry are re-derived on replay; a refused
  declaration stays dead; renewal, duration and cooldown caps hold.
- **Disputes.** Parties are never seated on their own case; the draw is integer
  and deterministic; enactment is idempotent, cannot exceed the disputed amount
  and cannot touch a settled transaction.
- **Reputation gates read the log, not the snapshot cache.**
- **Recovery and at rest.** The volume key reaches `cryptsetup` on stdin only;
  every subprocess is an argv spawn with no shell; zero keyslots is post-checked
  and `open` refuses any keyslot; the descriptor discloses only the address and
  the threshold; the strict mount guard runs before the database or wallet is
  touched; reconstruction is always checked against the target address; Shamir
  rejects index zero and duplicates without panicking.
- **CLI.** The wallet's station pin comes from `init --station`, not first use;
  receipts and certificates must be signed by the pin; the transport nonce is
  persisted before each use; no station-supplied bytes are signed beyond a
  32-byte anchor inside a kind-tagged entry; no verb takes or prints a secret;
  every PDF string is escaped and no output file name comes from a payload.
- **Scripts.** No `eval`, no `curl | sh`; `mktemp -d` with trap cleanup.

## Suggested order of remediation

1. **RRN-A-013** — a few lines, and it removes the unauthenticated halt. With
   it, panic containment and process exit on core death, which blunts every
   other panic in this report.
2. **RRN-A-014 and RRN-A-015** — bounds and sign rules in the marketplace
   validators, and the schedule on the admission clock. No design decision
   needed.
3. **RRN-A-016 and RRN-A-017** — one decision record on enrollment and on how
   standing accrues, then the implementation. These gate a pilot more than any
   other item: without them the debt floor and the electorate are not what the
   design says they are.
4. **RRN-A-018, 020, 021, 022** — contained fixes, each with a failing test
   described above.
5. **The ceremonies: RRN-A-023, 024, 029, 030.** Wire and fixture changes shared
   with the phone; each wants a dated ADR clarification first.
6. **Backup and at rest: RRN-A-031, 032, 046, 047, 049.**
7. **Governance: RRN-A-033, 034, 035, 043.**
8. **The CLI as the receiver's and member's tool: RRN-A-026, 027, 028, 044.**
9. The remaining Low items, and the documentation corrections — the red-team
   checklist in particular is handed to outside reviewers and should not
   describe defenses that are not there.
